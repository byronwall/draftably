### Exclusions from layout's public count

- Internal engine methods, target arrays, collision constants, annealing steps, topology caches, force coefficients, and diagnostic thresholds are implementation details. Explain their observable limits without turning them into knobs.
- Legacy JS aliases `radial` → `tree` and `compact` → `layered` are normalized by `settings` in `layout-engine.js:144–150`; the DSL rejects them. Record them in contributor notes only.
- `mode`, `warmStart`, `settle`, `maxIterations`, `fixedIds`, explicit scope objects, and related compute options are not new `.draft` attributes. Public editor controls using them are inventoried by the editor review.
- `aspect=canvas` exists in the editor settings, not the file grammar. It depends on the viewport and is intentionally omitted by `layout-edits.ts:60–61`.
- `separate` is an editor geometry repair, not an eleventh file engine. `layout-edits.ts:46–51` rejects serializing it as a recipe.
- Theme choice, color, typography, padding, count/badge decoration, heading/legend text, and generic export format/scale controls belong to the existing appearance/export reference. Typography and padding can affect measured node extents; freeze them in every causal atlas comparison and cross-link from sizing. They are not counted as additional layout algorithms or routing objectives. Node shapes and diagram width are included because they expose direct geometric/frame choices; DSL compare panel composition is included for the same reason. Generic `draftably compare` diff generation is cross-linked, while its layout-bearing panel direction/aspect are inventoried.

## Observed evidence from the attached engine comparison

`evidence/engine-variants.json` records ten attempted engine edits plus the unchanged current source. All eleven panels therefore represent ten engines, not eleven different algorithms. Baseline/current and explicit `compound-flow` both measure 1060×402, one crossing, twelve bends, and route length 1340. `layered` has exactly the same recorded geometry metrics and is tagged “same as v0”. This is positive evidence that a one-example selector cannot teach the difference between the engines.

`boundary-align` changes that fixture to 1277×606, zero crossings, nine bends, and length 1989. Its area is 81.6% greater and its total route length 48.4% greater than current. `compound-spring` changes it to 1131×721, zero crossings, nine bends, and length 1499: 91.4% more area and 11.9% more route length. Those are legitimate tradeoffs, not wins under every goal. `tidy` and `flow` share 1252×372, two crossings, and eleven bends, but route lengths differ (1209 versus 1243), so “same dimensions” must not become “identical result.” Every recorded warning count is zero. These conclusions apply to this one seven-node, three-group fixture.

The contact sheet is useful as evidence and weak as a teaching page: labels are small, each panel has a different apparent scale, and the thin routes make the cause of a changed crossing hard to locate. The atlas should preserve the actual renders, add selectable shared-scale comparison, show source edits, and offer a geometry/port overlay only for the examples where it explains an effect.

## Default and precedence model the docs must teach

1. No root layout statement means built-in flow with gap48. No child group recipe means column with gap24. An explicit ordinary recipe defaults gap28 (`compile.ts:827–839`, parser725–786).
2. File `direction=auto` resolves right in the fixed1100×720 compile context (`compile.ts:55`,636–640), not to the width of the docs viewport. Row and column already define their axes. Sequence uses its own horizontal participant layout.
3. File engine recipes are deterministic cold rebuilds: `mode:'rebuild'`, `warmStart:false`, `settle:true`, `maxIterations:640`, `growContainers:true` (`compile.ts:695–708`). The raw editor defaults—pass mode, maxMove48, stability65, iterations32, algorithmtidy—do not describe a file solve.
4. Nearest ancestor engine governs a framed descendant without its own layout statement. An explicit child recipe, including a built-in one, is a boundary. Ordinary nonengine parent recipes do not inherit into children (`compile.ts:643–649`). Soft/none groups dissolve into the nearest framed scope before layout.
5. Engine output is repacked, then hints apply; hints are not input forces in this cold compile path. `engineArrangement` strips every hint except size/order for the engine solve (`compile.ts:669–675`). A file pin can keep the final ordinary position exact while no longer influencing how the engine chose other positions.
6. Stay, nudge, and near are preferences with different weights; required alignment and near are constraints subject to pins. Collision repair and group clamping can move preferences. Stale stays can be dropped in pairs after growth (`compile.ts:1944–1989`,1997–2253). Cells, lanes, and sequence have specialized placement and must declare which hints they honor.
7. Routing follows final geometry and can consume compiler-generated lane/channel metadata. `constraint=false` removes an edge from layout ranking/engine topology but not from drawing, labels, or all route-space preparation. Edge-level details live in the routing audit.

## Algorithm terminology

Use the shipped labels plus concise mechanism descriptions. Avoid implying these are imported libraries or complete canonical algorithms.

- `layered` is a Sugiyama-style pipeline: deterministic cycle breaking, longest-path ranks, barycentric sweeps, and placement, followed by Draftably-specific packing/folding. Official ELK documentation is a useful primary explanation of the phases, not evidence that Draftably uses ELK: https://eclipse.dev/elk/reference/algorithms/org-eclipse-elk-layered.html and https://eclipse.dev/elk/blog/posts/2025/25-08-21-layered.html . Draftably source: `topology`, `layeredTarget`, `foldRanks`.
- `stress` performs weighted shortest-path stress descent with a diagonal approximation and collision/direction projection. Do not call it full stress majorization. The original paper defines the different majorization construction: https://graphviz.org/documentation/GKN04.pdf . Draftably source: `layout-engine.js:1368–1391`.
- `force` uses Fruchterman–Reingold-style attraction/repulsion and cooling, implemented with pairwise work; it is not a Barnes–Hut scalable solver. Original paper: https://onlinelibrary.wiley.com/doi/10.1002/spe.4380211102 . Draftably source: force branches1392–1409,1436–1456.
- `tree` builds a breadth-first spanning forest and allocates subtree spans. Do not promise a radial drawing, a Buchheim implementation, or an optimized drawing for every non-tree edge (`treeTarget`,478–522).
- `grid` uses canonical cell seeding for a cold rebuild and a greedy nearest-free-cell assignment in a warm pass (`gridTarget`,569–608). It does not solve a global matching problem.
- Compound flow, boundary alignment, and compound spring are original hierarchy-aware heuristics. They transmit endpoint influences across sibling owners and alternate hierarchy sweeps. They are not CoSE or an imported compound-layout package.

External pages were retrieved by web search during this review. Their primary-source URLs are recorded here for final citation; root should open them before citing retrieval IDs in the user-facing report.
