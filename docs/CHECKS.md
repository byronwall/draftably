# Checks

## Automated

```sh
pnpm check:fast   # typecheck, lint, format check, Vitest: about 10 seconds
pnpm check        # check:fast, the engine suites (about 80 seconds) and the build
```

Run `check:fast` while iterating and `check` before pushing. CI runs `pnpm release:check`, which
includes `check:fast`, the engine suites, and installed-package checks for the CLI, runtime, and Markdown adapter.

The runtime declaration files are generated by `pnpm runtime:build`. `pnpm typecheck` and
`pnpm test:unit` build them first, so both commands work from a clean checkout. `pnpm build` runs
typecheck before Vite. `check:fast` builds declarations through typecheck, then runs Vitest directly
to avoid a second runtime build.

Engine reports are written to the ignored `tmp/verification-current/` folder.

`pnpm runtime:build && pnpm runtime:pack-check` proves the portable runtime from its package archive.
`pnpm markdown:build && pnpm markdown:pack-check` builds and installs the Markdown adapter beside
the packed runtime. It checks Unified, MDX, markdown-it, includes, diagnostics, strict consumer types,
and asset replay after an output directory is cleared. `pnpm markdown:browser-check` checks the real
viewer client after the packed browser is installed.
`pnpm host:pack-check` installs the packed packages in fresh Astro/Starlight, Docusaurus, and
VitePress consumers. It copies the named config and setup snippets from the documentation into each
consumer. It runs two clean production builds per host, edits an included source between builds,
and verifies that each nested-base image URL points to an SVG in the output directory.
Pass `astro-starlight`, `docusaurus`, or `vitepress` to check one host, such as
`pnpm host:pack-check vitepress`.
The host proof requires Node 22.22.0 or newer for Astro 7.4.5.

## Performance

`pnpm bench` times CLI commands and viewer interactions on the five diagrams in
`scripts/bench/diagrams/` (6 to 28 boxes, and a sequence) against two budgets: interactive actions
under 200 ms and document load under 1 s. Viewer times run from the input until the drawing is
settled: not compiling, layout idle, saved, and geometry unchanged for 250 ms. It prints a Markdown
table with ✗ on each time over budget and writes the medians to `tmp/bench/latest.json`.

```sh
pnpm bench                                     # 3 runs each, about 15 minutes on main today
pnpm bench --only cli --files xl               # one part, some diagrams
pnpm bench --out tmp/bench/after.json --compare tmp/bench/before.json   # before → after cells
```

`pnpm bench:graph` builds the runtime and lays out each graph in `scripts/bench/graph-corpus.mjs`
through `@draftably/runtime/graph`: edge cases (empty, self loops, awkward IDs, nested groups) and
chains, trees, DAGs and architectures of up to 100 nodes. It fails on a throw, a missing ID,
overlapping boxes, a child outside its group, a line that misses its boxes, or different output
for the same input. It reports blocked lines and times over the 1 s load budget. Add
`--quality full|quick` to time one router mode, and `--only <name>` for some graphs.

`pnpm bench:fresh` times `layout()` on a new random graph for every call (a tree of 100 nodes and
DAGs of 50, 100 and 200 nodes), so the router's cache never helps, as with a host that lays out a
graph once. It reports the median time and drawing measures (crossings, bends, length, lines
through boxes, blocked lines, area) and a digest of every drawing. The graphs come from fixed
seeds, so an equal digest proves a speedup changed no drawing. Keep the default 5 runs when you
compare digests. Add `--quality quick|full`, `--only <name>`, `--out <file>` and
`--compare <file>` for a before → after table.

CI runs it once per change as a non-blocking `bench` job and puts the table in the job summary.
Performance PRs paste a before → after table.

### Host contract budgets

`pnpm bench:host` (also the last part of `pnpm bench`, or `pnpm bench --only host`) builds the
runtime and loads the built `<draft-diagram>` on plain pages in Chromium, with no bundler. It
measures the budgets in [the host contract plan](intent/host-contract/plan.md#performance) and
prints median and p95 per row with ✓ or ✗. Add `--runs N` (default 5) and `--strict` to fail on ✗.

| Area                                         | Budget                                                    |
| -------------------------------------------- | --------------------------------------------------------- |
| Main-thread JS, viewer-only page             | ≤ 40 KB gz; no editor request                             |
| First diagram, 28-box file, cold (4× CPU)    | ≤ 1 s                                                     |
| First diagram, 28-box file, warm             | ≤ 300 ms (not met: see below)                             |
| 20 instances of the 28-box file              | every diagram commits; no timeouts                        |
| Source update to commit, 28 boxes            | ≤ 200 ms                                                  |
| Workers, 20 instances × 20 updates           | ≤ min(4, cores − 1) render workers per page               |
| 20 instances: stylesheets, fonts, long tasks | 1 sheet; 1 font set; no long task over 200 ms             |
| `geometry()` at 200 nodes                    | ≤ 1 ms; the same object for one revision                  |
| Camera frame, 10 / 100 / 500 slot targets    | ≤ 8 ms p95 at 500; 0 forced layouts                       |
| Target reconcile per update, 500 targets     | ≤ 10 ms; no target re-created for an unchanged ID         |
| Editor drag frame, 200 nodes, 400 targets    | ≤ no slots + 5 %; no anchors event, re-observe or assign  |
| Mount and destroy, 50 cycles                 | heap within 5 %; listeners, workers and fonts at baseline |

Each change from the host contract on must keep every ✓ row ✓ and must not make a ✗ row slower.
The warm first diagram is bound by a fresh layout of the 28-box file (about 600 ms of router work
on an M3 Pro, before any cache), not by the runtime. The CPU throttle slows the page, not the
worker, so the cold row mostly measures the same layout.

The slot rows use a 250-node file with a body and an overlay on the first N / 2 nodes. A camera
frame is one `setCamera` plus the style and layout it causes; the bench reads layout once after
the move to include that cost. Forced layouts are counted as layout reads during 100 moves: the
bench wraps every DOM API that reads layout, and a forced layout needs one. Reconcile times `viewer.anchor()` with the same 500 slots, which runs the
pass a commit runs over every target. A source update that moves every node must then add and
remove no target.

The drag rows load one `<draft-editor>` of a 200-node file, with no slots and then with a body and
an overlay on each node, and drag a node 60 moves. A frame is the `pointermove` dispatch plus the
style and layout it causes. With slots it must fire no `anchors` event, call no
`ResizeObserver.observe` and no `slot.assign`, and stay within 5 % of the frame with no slots. The
frame is slow at 200 nodes either way (about 215 ms on an M3 Pro): each edge view scans every edge
on each move.

## Slots

`pnpm prove:slots` loads the built `<draft-diagram>` and `<draft-editor>` on one plain page in
Chromium, Firefox and WebKit, each with host children marked `data-draft-slot`. Build first with
`pnpm runtime:build && pnpm editor:build`; pass `chromium`, `firefox` or `webkit` to run one. For
both elements it checks: `host.css` hides content before the elements define; each marked child is
assigned to its target; targets follow drawing order; an unknown slot is a `DRAFT_SLOT_UNKNOWN`
warning; a body fills its node and scales with the camera; an overlay sits at its item's screen box
at screen scale; host CSS styles the content; a click on body text reaches the drawing, not the
card; a
`data-draft-input` button takes its click and only it; a caret survives a source update; content
follows an update and keeps its target; `overflow: clip` never scrolls on focus; focus in a body
reveals it; low detail hides bodies and shows titles; a commit made below zoom 0.4 still hides the
titles under bodies at zoom 1; content larger than its node, assigned after its target exists, is a
`DRAFT_SLOT_OVERFLOW` warning. For the editor also: its styles are adopted in
its shadow root; a page value for a token wins; `data-theme="dark"` switches the tokens; ports and
resize handles of a body node sit above the body and resize it; typing **N** in a marked input adds
no node; and both send `anchors` with `[]` on removal. Screenshots go to `tmp/proof-slots/`.

`pnpm prove:color-scheme` loads the built elements on one plain page in Chromium, Firefox and
WebKit: a viewer and an editor of a source with no `theme` line, a viewer forced light with
`color-scheme: light`, a viewer of a source with `theme fieldnotes`, and one with
`theme drafting`. A light page draws all of them light. `color-scheme: dark` on the page draws the
viewer, the editor and the `theme drafting` one dark, with no new render and no moved box, and the
forced and fieldnotes ones keep their colors. With no `color-scheme` on the page, a dark system
setting leaves all of them light; `color-scheme: light dark` or `dark` on the page then draws them
dark. It also checks a host hidden while the page turns dark, a viewer and an editor mounted
detached with no shadow root, the light-DOM editor's `data-theme`, and a page with
`* { transition: none !important }`. Build first, as for slots. Screenshots go to `tmp/proof-color-scheme/`.
`pnpm prove:frameworks` also checks that each wrapper's diagrams stay light on a dark system
setting until the page sets `color-scheme: light dark`, then draw dark, and saves `tmp/frameworks/<framework>-dark.png`.

`pnpm prove:frameworks` (CI) runs the checks that depend on the host through the React, Solid,
Vue and Svelte wrappers in Chromium, with the content rendered and updated by each framework:
pass-through and assignment, the unknown-slot warning, geometry and camera scale, host CSS, orphan
content, pointer pass-through, a marked button, a caret across an update, content that follows a
framework update with the same target, `overflow: clip`, and in the editor assignment, body
placement, selection through body text and no shortcut from a marked input.

## Hosts

Every host runs one list of checks, `scripts/lib/host-proof.ts`, against a server-rendered page
that shows the proof page in `integration-examples/frameworks/proof.js`. With real mouse and
keyboard input in Chromium it checks: the server HTML holds the diagram's SVG, the slot content
and both editors; hydration keeps the server's nodes, with no console errors or hydration
warnings; a body reads the framework's context and page CSS and fills its node; a marked button
takes its click and the drawing does not; a caret survives a source update; **Delete** in one
editor changes only that editor; a failed update keeps the drawing and shows its message; the
page is served with a strict nonce CSP (no `'unsafe-inline'`) and reports no violation; and 50
mount cycles of a viewer and an editor end with heap within 5 % and listeners, workers and fonts
at baseline. Screenshots and the server HTML go next to each run's output.

- `pnpm prove:frameworks` (CI) runs it on each Vite app's `proof.html`, after the app's own
  checks.
- `pnpm prove:meta [next solid-start nuxt sveltekit]` builds each app in
  `integration-examples/meta/` for production with the packed packages, starts its server and
  runs it there. Each app holds a copy of its proof page, so it runs on its own;
  `proof.config.json` names the copies and the build and start commands. A copy that differs from
  its source in `integration-examples/frameworks/` fails the run: `pnpm prove:meta --write`
  refreshes them. Installs take minutes (Next.js downloads about 80 MB), so run it in the
  background. It is not in CI. Output goes to `tmp/meta/`.

`pnpm prove:recipes` (CI) copies every named code block in the "Build the app" section of each
framework page (`site/docs/pages/react.md`, `solid.md`, `vue.md`, `svelte.md`, `plain-html.md`)
into a fresh Vite app, and installs only the packed packages that the recipe's `pnpm add` line names. It type-checks (`tsc`, `vue-tsc` or `svelte-check`),
builds, calls the recipe's server `render()`, and loads the page: the diagram and the editor must
reach `status="ready"` with the body assigned, the dark frame applied, and no console errors. Then it
starts `vite` in development and deletes a node in the editor, which fails on a worker 404. A
recipe that stops compiling fails CI. Screenshots go to `tmp/recipes/`.

`tests/site-docs.test.ts` keeps the meta-framework CSP and config code on each framework page the
same as the files in `integration-examples/meta/`, which `pnpm prove:meta` builds and checks.

## File-backed editing

`tests/file-session.test.ts` checks the first title entered after a new shape receives its source
ID. It also checks selection and the active title editor after projection. `tests/edge-labels.test.ts`
checks labels across short gaps, group headers, existing labels, and long text.

`pnpm cli:build && pnpm prove:installed` packs draftably, installs the archive in a fresh temporary
project, and runs its executable outside the repository. It checks help, validation, formatting,
repeatable JSON, SVG, bundled viewer assets, API saves, and conflicts. It then runs the browser proof
below against the installed CLI. Only the proof harness uses the repository's Playwright dependency.
The installed product has no runtime package dependencies or install scripts.

GitHub's Check workflow and the release gate run `pnpm release:check`, including the clean-install
CLI and HTTP proof. The workflow's `proofs` job runs `prove:file` and `prove:layout` in Chromium
and uploads their screenshots when they fail.

Both browser proofs share `scripts/lib/proof.mjs`. It starts `draftably open --port 0`, so a proof
never collides with another worktree's viewer. When a check fails, the summary names it and the
output folder gets `failure.png` (the page at the end of the run) and `failure.json` (failed checks,
the viewer's file state and the last 50 console lines). One failed run is enough to start
diagnosing; don't rerun until it passes.

`pnpm build && pnpm prove:file` drives the real editor in Chromium (`playwright-core` with an
installed Playwright Chromium) against a temporary copy of `examples/checkout.draft` served by
`pnpm draftably open`. It resizes a group, drags a sibling, pins an object, moves the camera, undoes and
redoes, appends a connected node from outside, restarts the server, writes invalid source, and
races an outside write against a viewer save. At each step it compares the browser's geometry
with `pnpm draftably inspect --json`. Screenshots go to `tmp/proof/`. It takes about 10 seconds.
It launches full Chromium rather than the headless shell the other proofs use, so on a new
machine run `pnpm exec playwright-core install chromium` once; without it the proof stops at
once and prints that command.

The file proof also switches between more than six diagrams with Chrome’s back/forward cache enabled, then restores a cached page after an external file change. This catches retained EventSource connections that can exhaust the browser’s HTTP/1 pool; Playwright disables that cache by default.

To serve a folder from the dev server instead, run `DIAGRAM_ROOT=folder pnpm dev`.
`DIAGRAM_FILE=path/to/file.draft pnpm dev` serves the current folder and prints the file's address.

## Portable runtime

`pnpm runtime:build && pnpm runtime:pack-check` builds and installs the runtime tarball in a temporary consumer outside the repository. It checks native diagrams, repeatable SVG, embedded fonts, dependency isolation, and NodeNext TypeScript imports. The report records actual archive, static module, font sizes, and first/repeat render times.

`pnpm prove:runtime` loads the copied installed distribution below a nested URL in Chromium. It verifies module chunks, the finished SVG image, and console errors. Run the pack check first to prepare its consumer. CI runs both proofs; neither publishes a package.

`pnpm viewer:pack-check` installs the packed runtime in fresh Node, vanilla, React, and Solid consumers. It checks declarations, SSR-safe imports, the emitted worker asset, and framework builds. `pnpm prove:viewer` serves the packed browser fixture below a nested path and checks worker updates, lifecycle races, camera behavior, links, and blocked worker/font policies. It also runs React Strict Mode and Solid lifecycle fixtures in Chromium. Run `pnpm runtime:build && pnpm viewer:pack-check` first; output goes to `tmp/viewer-proof/`.

The viewer pack check also builds the diagram element example. `pnpm prove:element`
checks its real worker, source updates, fallback, removal and reconnection,
keyboard controls, narrow layout, and isolation from host styles.

## The public site

`pnpm docs:assets` refreshes the comparison study's published sources, supporting documents and
download ZIP from the originals. Commit the generated files with any study change.
`tests/site-downloads.test.ts` rejects stale copies or a stale ZIP during `check:fast` and opens
the archive with `unzip` (included on macOS and the Ubuntu CI runner).

`pnpm site:build && pnpm prove:site` serves `dist-site/` the way GitHub Pages does and drives it in
Chromium with real clicks and keys. It covers the links between surfaces, narrow Playground panes,
docs overlays, export blocking, reopening an exported image, and a failed module load. Direct URLs
miss most of these failures, so a journey clicks what a visitor clicks. Pass a word from a journey's
name to run one: `pnpm prove:site narrow`. Screenshots go to `tmp/proof-site/`.

## Themes in file mode

`pnpm build && pnpm prove:themes` serves a temporary copy of `examples/theme-proof.draft` on a free
port and drives the editor in Chromium. With Fieldnotes it checks serif node and group titles,
real text bounds inside every shape, group titles clear of their content, geometry equal to
`draftably inspect`, and that the browser SVG, CLI SVG and PNG exports render the embedded fonts
on their own. It then saves a shade change (nothing moves), restarts the server, writes an invalid
theme and a padding change from outside, renders all five themes from source, and uses the
**Appearance** menu to change theme and padding with undo and redo. Screenshots and exports go to
`tmp/proof-themes/`.

## Layout tools in file mode

`pnpm build && pnpm prove:layout` drives the editor against a temporary copy of
`examples/order-pipeline.draft`. It applies a Compare candidate (a layout recipe), runs Improve,
keeps a timeline step and paints a brush stroke (positions), appends a node from outside, and
restarts the server. After every step the browser's geometry must equal `draftably inspect` of
the saved file, and the arranged region away from the addition must not move. Screenshots go to
`tmp/proof-layout/`.

## Two editors on one page

`pnpm prove:editors` serves `tests/browser/two-editors.html` through Vite. The page mounts two
editors with `mountEditor`. The proof drags, selects, adds a node and undoes in one editor with real
mouse and keys. The other editor's document, selection and source must not change. Screenshots go to
`tmp/proof-editors/`.

## Links in file mode

No script covers this. Run `pnpm draftably open tests/fixtures/links.draft` and click each ↗
mark. A URL opens as written in a new tab, `examples/theme-proof.draft` opens in the viewer, and a
file path opens the editor at its line, from the git root. A click on a box away from its mark only
selects it.

## Browser

The SolidJS rewrite was exercised in Chrome (the Claude desktop browser pane) at 1440 × 900 and
820 × 700, in light and dark themes, through real pointer and keyboard input plus
`window.diagramStudio` for state inspection:

- Startup, restore from browser storage, and examples loaded through the File menu with confirmation.
- Shape drag with snapping, dropping into and out of containers, undo and redo.
- **N**, typing, **Tab** to extend, **Enter** to commit; quick-add buttons; Connect tool with preview.
- Drawing and naming a container, moving it with its contents, collapsing it.
- Inspector edits: label, color, shape, position, pin; edge bends by double-click.
- Copy, paste, paste-a-list into Build from a list, object search.
- Layout pass, previewed rebuild with discard, layout lab (**Alt+L**), routing menu, Reroute.
- Compare: six candidates, grid fitting, overlay with layers, Apply and Undo.
- Timeline: record, scrub, Keep & brush; brush hover preview and a committed stroke.
- Editable SVG export and re-import, PNG conversion.

## Not covered

- Native file pickers and drag-and-drop of files (the import code paths are shared with paste and
  were exercised that way).
- Safari, Firefox, touch input and trackpad gestures.
- A full accessibility audit.

The layout engines are heuristics: they can leave crossings or ordering conflicts and do not
promise a globally optimal drawing.

## Diagram quality audit

`node scripts/diagram-audit.mjs docs/intent/diagram-quality/corpus tmp/audit/rN` measures the
audit corpus and writes metrics, PNGs, contact sheets and `summary.md`. The rubric, the corpus
rules and the round loop are in
[intent/diagram-quality/RUBRIC.md](intent/diagram-quality/RUBRIC.md); past rounds are in
`rounds/`.

- A full run with screenshots takes about 90 seconds. While iterating on one cause, pass
  `--only slug,slug` and `--no-shots`, then do a full run before the PR.
- Run full rounds in the background and wait for them to finish; don't poll with sleep loops.
- `--baseline tmp/audit/rN-1` adds before/after `compare-*.png` sheets for PR screenshots.

To measure a fix, use `pnpm audit:compare` instead of hand-built baselines, corpus copies and
diff scripts. It audits the corpus, the held-out diagrams and `examples/` against
`origin/main` and against the working tree, in parallel. Both sides use this checkout's audit
script and inputs, so only the engine differs. It then prints `compare.md`: mean defect index
per set, the issue kinds whose counts changed, and the renders that moved most.

- `--base <ref>`, `--sets corpus,heldout,examples`, `--only slug,slug`, and `--shots` for the
  images and before/after `compare-*.png` sheets (slower). Output goes to `tmp/audit/compare/`
  (`--out` to change it).
- The base ref is checked out once into `tmp/audit-base/<sha>`, and its results are cached
  there, so later runs only audit the working tree.

## Screenshots

`pnpm shoot <target> tmp/out.png` captures a URL, a `.draft` file (drawn through
`draftably inspect --svg`), or an SVG, PNG or HTML file. `pnpm shoot --sheet tmp/sheet.png
Label::a.draft b.draft …` lays several targets out as a labeled contact sheet. `--crop x,y,w,h` zooms
in on one region at 2x, in the target's own pixels. Use it for PR screenshots and visual checks
instead of writing a one-off Playwright script or an image library. Keep the output in the
ignored `tmp/` folder.
